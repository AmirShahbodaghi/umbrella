# Kubernetes Deployments with Argo CD and a Shared Helm Chart

This document describes our GitOps deployment structure using Argo CD, ApplicationSets, and the shared `helm-generic` Helm chart.

Application configuration is stored in Git. Argo CD renders the chart with each application's values file and reconciles the resulting Kubernetes resources.

> **Scope:** This guide is based on the supplied Argo CD manifests and repository layout. The chart templates and values schema have not been inspected. Application-specific values must follow the actual chart schema. The repository is referred to as an umbrella chart internally; whether it uses Helm chart dependencies is defined in `Chart.yaml`.

## 1. Architecture

```text
argocd-apps repository
  rootapp.yml                         Applied once during bootstrap
      |
      v
  root-app (Argo CD Application)
      |
      | Reads appsets/*.yaml
      v
  general-apps (ApplicationSet)
      |
      | Scans helm-generic: values/general/*.yaml
      v
  One Argo CD Application per matching values file
      |
      | Renders helm-generic at repository root
      | with values.yaml + values/general/<application>.yaml
      v
  Kubernetes resources in the general namespace
```

The root application manages ApplicationSets, not Helm workloads directly. The ApplicationSet controller creates and updates the child Applications. Argo CD then deploys the workloads defined by those Applications.

### Namespaces

| Namespace | Purpose |
| --- | --- |
| `argocd` | Argo CD and its Application, ApplicationSet, and AppProject resources |
| `general` | Workloads generated by `general-apps` |

The Kubernetes destination is the cluster where Argo CD runs: `https://kubernetes.default.svc`.

## 2. Repository Layout

Recommended layout for `argocd-apps`:

```text
argocd-apps/
├── README.md
├── rootapp.yml
├── projects/
│   └── platform-admin-project.yaml
└── appsets/
    └── general.yaml
```

Existing `helm-generic` layout, as shown in the repository screenshot:

```text
helm-generic/
├── Chart.yaml
├── values.yaml
├── templates/
└── values/
    ├── general/
    │   ├── payeshnotify.yaml
    │   ├── requestback.yaml
    │   └── requestfront.yaml
```

The provided ApplicationSet only processes `values/general/*.yaml`. Other folders need their own ApplicationSet or another explicit generator configuration; creating a folder alone does not enable deployment.

## 3. Configuration Review

The supplied manifests have several important differences from the intended project isolation:

| Supplied configuration | Meaning / correction |
| --- | --- |
| `root-app.spec.project: default` | The `platform-admin` project does not govern `root-app`. Use `platform-admin` if that restriction is intended. |
| `platform-admin.sourceRepos` points to `devops/cd/test/general/argocd-apps.git` | This differs from the root application's actual repository. Allow the `devops/cd/umbrella/argocd-apps.git` URL instead. |
| AppProject and ApplicationSet appear in `clusterResourceWhitelist` | Both are **namespaced** resources. Put them in `namespaceResourceWhitelist`. |
| Root directory filter is `appsets/*.yaml` | Project definitions under `projects/` are not synchronized by this root application. Bootstrap them separately. |
| Generated Applications use project `default` | They remain governed by `default`, independently of the root application's project. Use dedicated workload projects for stronger isolation. |

The manifests below use a corrected `platform-admin` project for the root application and retain `default` for workloads to match the current deployment model.

> **Security:** Allowing an application to deploy resources into the Argo CD namespace is privileged. AppProjects and ApplicationSets can influence what other applications deploy. Restrict write access to `argocd-apps`, require reviewed changes, and protect `main`. This bootstrap project is not a security boundary for untrusted contributors.

## 4. Argo CD Manifests

### 4.1 Bootstrap Project — `projects/platform-admin-project.yaml`

Apply this project before creating `root-app`.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: platform-admin
  namespace: argocd
spec:
  description: "Administrative project for GitOps bootstrap resources"
  sourceRepos:
    - "https://gitlab.ir/devops/cd/umbrella/argocd-apps.git"
  destinations:
    - namespace: argocd
      server: https://kubernetes.default.svc
  clusterResourceWhitelist: []
  namespaceResourceWhitelist:
    - group: argoproj.io
      kind: AppProject
    - group: argoproj.io
      kind: ApplicationSet
    - group: argoproj.io
      kind: Application
```

This permits only the listed namespaced resource kinds, with no cluster-scoped resources allowed. With the current root directory filter, only ApplicationSets are needed; the additional kinds support administrative expansion and can be removed if unused.

Project permissions do not replace Kubernetes RBAC. Argo CD's controllers must also have the required cluster permissions.

### 4.2 Root Application — `rootapp.yml`

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: root-app
  namespace: argocd
  finalizers:
    - resources-finalizer.argocd.argoproj.io
spec:
  project: platform-admin
  source:
    repoURL: https://gitlab.ir/devops/cd/umbrella/argocd-apps.git
    targetRevision: main
    path: .
    directory:
      recurse: true
      include: "appsets/*.yaml"
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true
```

- `recurse` enables directory traversal; `include` limits which files are rendered.
- `prune` allows removal of previously managed resources no longer present in the desired manifests, subject to Argo CD's safety settings.
- `selfHeal` reconciles manual changes back to Git's desired state.
- `CreateNamespace=true` requests creation of the destination namespace if needed and permitted. Argo CD itself must already be installed in `argocd`.
- The finalizer enables cascading deletion of managed resources when the Application is deleted.

Neither `rootapp.yml` nor `projects/platform-admin-project.yaml` is managed by this root application because neither matches `appsets/*.yaml`. Apply changes to these bootstrap files explicitly through the approved bootstrap process.

### 4.3 General ApplicationSet — `appsets/general.yaml`

```yaml
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: general-apps
  namespace: argocd
spec:
  generators:
    - git:
        repoURL: https://gitlab.ir/devops/cd/umbrella/helm-generic.git
        revision: main
        files:
          - path: "values/general/*.yaml"
  template:
    metadata:
      name: "{{appName}}"
      namespace: argocd
    spec:
      project: default
      source:
        repoURL: https://gitlab.ir/devops/cd/umbrella/helm-generic.git
        targetRevision: main
        path: .
        helm:
          valueFiles:
            - "{{path}}/{{path.filename}}"
      destination:
        server: https://kubernetes.default.svc
        namespace: general
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
          - CreateNamespace=true
```

This uses the ApplicationSet's legacy templating syntax, as in the supplied configuration. Do not enable `goTemplate: true` without migrating the expressions: the corresponding Go-template expressions are `{{ .appName }}` and `{{ .path.path }}/{{ .path.filename }}`.

Each matching file must contain a top-level `appName`:

```yaml
# values/general/payeshnotify.yaml
appName: payeshnotify

# Add the deployment values required by the actual chart.
```

This snippet illustrates the generator field only; it is not a complete workload configuration. If the chart enforces a values schema, ensure that schema permits `appName`.

For this file, the generated Application uses:

| Setting | Value |
| --- | --- |
| Application name | `payeshnotify` |
| Application namespace | `argocd` |
| Chart directory | Repository root (`.`) |
| Additional values file | `values/general/payeshnotify.yaml` |
| Workload namespace | `general` |

Helm loads the chart's default `values.yaml` and merges the application-specific values over it. Argo CD uses Helm to render manifests; Argo CD, rather than a separately managed Helm release, manages their lifecycle.

Application names must be valid Kubernetes resource names and unique among Applications in `argocd`. The chart must also generate non-conflicting Kubernetes resource names when multiple applications share `general`.

## 5. Prerequisites and Bootstrap

Before bootstrap, confirm:

- Kubernetes is available and the intended context is selected.
- Argo CD, its CRDs, and the ApplicationSet controller are installed.
- Argo CD can authenticate to **both** private Git repositories.
- Repository TLS certificates are trusted by Argo CD.
- Argo CD has permission to create the required resources and namespaces.
- The workload project (`default` in this example) permits the Helm repository, destination, and required resource kinds, including Namespace creation if needed.
- Container registries are reachable and workload image pull credentials are configured.
- Required external CRDs, storage classes, ingress controllers, and secrets exist where the chart needs them.

From a checkout of `argocd-apps`:

```bash
kubectl config current-context
kubectl apply -f projects/platform-admin-project.yaml
kubectl apply -f rootapp.yml
```

The root application should create `general-apps`. The ApplicationSet controller should then generate the child Applications.

Check progress:

```bash
kubectl -n argocd get appprojects
kubectl -n argocd get applicationsets
kubectl -n argocd get applications
kubectl -n general get deployments,statefulsets,daemonsets,pods,services,ingresses
```

With an authenticated Argo CD CLI:

```bash
argocd app get root-app
argocd app get payeshnotify
argocd app wait payeshnotify --sync --health --timeout 300
```

Reconciliation is asynchronous. A Git commit does not imply immediate deployment.

## 6. Deploy a New Application

1. Create a branch in `helm-generic`.
2. Copy a suitable existing file from `values/general/`.
3. Set a unique `appName` and the chart-supported application settings.
4. Check image references, ports, resource requirements, probes, ingress, and secret references as applicable.
5. Render and validate locally.
6. Open a merge request and merge the reviewed change into `main`.
7. Confirm that the generated Application becomes `Synced` and `Healthy`.

Example validation from the `helm-generic` repository root:

```bash
# Run if Chart.yaml defines dependencies and Chart.lock is committed:
helm dependency build .

helm lint . -f values/general/my-service.yaml
helm template my-service . \
  --namespace general \
  -f values/general/my-service.yaml > /tmp/my-service-rendered.yaml
```

Use an `appName` of `my-service` for this example. Do not assume keys such as `image`, `replicaCount`, or `ingress` exist: follow the actual chart's `values.yaml`, templates, and schema.

Inspect rendered resource names, namespaces, selectors, ports, and secret references. Helm validation alone does not confirm cluster admission policies, CRD availability, or runtime readiness.

> Matching `*.yaml` files are deployment inputs, not general-purpose documentation. Do not place examples or unrelated YAML in `values/general/`. Files ending in `.yml` do not match this generator pattern.

## 7. Update, Roll Back, and Remove Applications

### Update

Change the application's values file, validate it, and merge to `main`. Automated sync applies the new desired state.

Changes to shared templates or chart defaults can affect **every application using this chart and revision**, not only one values file. Test representative applications and review the wider impact before merging.

### Roll back

Prefer a Git revert so that the desired state remains auditable:

```bash
git revert <commit-sha>
git push origin <rollback-branch>
```

Open a merge request from that branch into `main`. Reverting a shared chart change can affect multiple applications. Reverting manifests does not restore deleted data or reverse database migrations.

Avoid relying on manual edits or an imperative rollback while Git still specifies the newer state: reconciliation can restore it.

### Remove

Removing a matching values file normally causes the ApplicationSet controller to remove its generated Application. Under the normal default ApplicationSet behavior, generated Applications carry resource-deletion finalizers, so their workloads can also be deleted.

Removing an ApplicationSet manifest or deleting `root-app` can cause a broader cascade. Controller policies, preservation settings, and empty-application safeguards can alter the outcome; inspect them before any removal.

**Before deletion:** obtain approval, confirm backups and persistent-volume retention behavior, and review exactly which Applications and resources will be affected. Do not treat file deletion as a way to pause an application.

## 8. Add Another Environment or Application Group

For a folder such as `values/finance-dev/`, create a separate ApplicationSet in `argocd-apps/appsets/` and update:

| Field | Example |
| --- | --- |
| `metadata.name` | `finance-dev-apps` |
| Git generator file path | `values/finance-dev/*.yaml` |
| Destination namespace | `finance-dev` |
| Workload project | An approved project for that environment |

Bootstrap the workload project before using it. It must allow the chart repository, destination, and required resource kinds.

With the current naming template, use environment-qualified `appName` values, such as `finance-dev-api` and `finance-prod-api`, to avoid collisions in `argocd`.

Do not deploy the same Kubernetes resource from two Applications. Namespace and resource naming must keep ownership unambiguous.

## 9. Troubleshooting

| Symptom | Checks |
| --- | --- |
| `root-app` cannot sync | Check repository access, `platform-admin` existence, source URL, destination permissions, and namespaced resource whitelist. |
| ApplicationSet is missing | Check that its file is under `appsets/`, ends in `.yaml`, and is selected by the root application's directory filter. |
| Child Application is missing | Check the generator glob, branch, YAML validity, top-level `appName`, duplicate names, and ApplicationSet status. |
| Values file cannot be found | Inspect the generated Application's `spec.source.helm.valueFiles`; it should be relative to the chart directory. |
| Repository or destination is not permitted | Check the affected Application's own `spec.project`, not only the root application's project. |
| Namespace creation is forbidden | Check workload project permissions and Argo CD's Kubernetes RBAC; alternatively pre-create the namespace. |
| Helm rendering fails | Run `helm lint` and `helm template`; check dependencies, required values, and the chart schema. |
| Application is synced but unhealthy | Inspect workload events, pod logs, image pulls, probes, secrets, quotas, and storage. |
| Manual edits disappear | `selfHeal: true` restores Git's desired state. Make persistent changes in Git. |
| A new environment folder does nothing | The supplied ApplicationSet watches only `values/general/*.yaml`. |

Useful commands:

```bash
kubectl -n argocd describe application root-app
kubectl -n argocd describe applicationset general-apps
kubectl -n argocd get application payeshnotify -o yaml
kubectl -n general get events --sort-by=.metadata.creationTimestamp
kubectl -n general describe pod <pod-name>
kubectl -n general logs <pod-name> --all-containers=true --tail=100
```

For controller errors, locate the ApplicationSet controller pod in `argocd` and inspect its logs. Controller names and installation labels may differ between installations.

## 10. Operational Guidelines

- Protect `main` and require review for chart, values, and bootstrap changes.
- Use immutable image tags or digests for reproducible deployments.
- Keep plaintext secrets and repository credentials out of Git; use an approved secret-management solution.
- Prefer dedicated workload AppProjects over `default` for environment isolation.
- Validate all affected values files when modifying shared templates or chart defaults.
- Monitor both sync status and application health.
- Review pruning and cascading-deletion implications before renaming `appName`, moving values files, or removing manifests.
- Keep a tested backup and recovery process for stateful services.

### Deployment Checklist

- [ ] Values file matches the intended ApplicationSet path and extension.
- [ ] `appName` is valid and unique.
- [ ] Chart values and rendered manifests are validated.
- [ ] Project permissions and destination namespace are correct.
- [ ] Images, secrets, storage, and required infrastructure are available.
- [ ] Changes are reviewed and merged into the tracked branch.
- [ ] Argo CD reports `Synced` and `Healthy`.
- [ ] Service behavior is verified after deployment.
